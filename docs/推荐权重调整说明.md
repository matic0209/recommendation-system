# 推荐权重与推荐策略调整说明

> 更新时间：2026-02（本次改动）
> 相关文件：`app/main.py`、`pipeline/build_training_labels.py`、`pipeline/train_models.py`
> 关联文档：[推荐系统算法说明](./RECOMMENDATION_ALGORITHM.md)、[环境变量配置](./ENVIRONMENT_CONFIG.md)

本文说明：**推荐权重到底由谁决定**、**本次做了哪些小幅度调整**、**以后要调力度/分类应该改哪里**、**怎么验证和回滚**。

## 一、权重不是一张表：四层叠加，最后一层才真正生效

推荐分数由多个渠道加权融合而来，而**权重会被逐层覆盖**。改之前一定要先搞清楚改的是哪一层：

| 层级 | 位置 | 说明 | 改完怎么生效 |
|------|------|------|-------------|
| ① 代码默认值 | `app/main.py` 的 `DEFAULT_CHANNEL_WEIGHTS` | 服务的兜底权重 | 需**重启容器** |
| ② 每日 CTR 训练结果 | `models/channel_weights.json`（由 `pipeline/train_channel_weights.py` 每天重算，Airflow `recommendation_pipeline`） | **覆盖 ①中 behavior/content/vector/popular 四项** | 改文件后 `POST /models/reload`；**次日会被流水线覆盖** |
| ③ 实验变体 | `config/experiments.yaml` | 只作用于 `/recommend/detail`，按 allocation 切流 | **热加载，无需重启**（watchdog 监听） |
| ④ 每次请求的动态调整 | `app/main.py` 的 `_compute_dynamic_channel_weights` | 数据稀疏时把权重从一个渠道转给其他渠道 | 代码内逻辑，随代码生效 |

**关键结论：只要 `models/channel_weights.json` 存在，①中的 behavior/content/vector/popular 就不生效。** 所以调权重前先确认线上这份文件的实际内容：

```bash
cat models/channel_weights.json                     # 宿主机（docker-compose 挂载 ./models）
docker exec recommendation-api cat /app/models/channel_weights.json   # 容器内
```

### 业务规则（2026-02 与业务方确认，**代码已强制**）

**权重次序：vector（语义）= content（内容/标签） > behavior（行为协同） > popular（全局热门）**

这条规则不再依赖"配置文件写对"，而是由代码兜底（`_enforce_channel_weight_order`，`app/main.py`）：

| 规则 | 参数 | 默认值 | 作用 |
|------|------|--------|------|
| 单渠道限幅 | `CHANNEL_WEIGHT_OVERRIDE_BAND` | 0.4 | 每个渠道最多在默认值的基础上下浮动 ±40%，防止 CTR 训练结果把某渠道压到接近 0 或抬到失真 |
| 层级最小间距 | `CHANNEL_WEIGHT_MIN_GAP` | 0.15 | 上一层至少比下一层高 15%，保证次序不被反转 |
| popular 占比上限 | `MAX_POPULAR_SHARE` | 0.25 | 最终列表里 popular 来源最多占 25%（12 条 → **3 条**） |
| 单一类别占比上限 | `MAX_OTHER_CATEGORY_SHARE` | 0.25 | 除"目标数据集自身行业"外，单一行业类别最多占 25%（12 条 → 3 条） |

因此：即使每日 CTR 流水线把 `popular` 训成最高权重，线上也会被限幅并压回三级——**"权重被训练结果意外反转"这个长期隐患被消除**。

### 线上问题复盘（本次调整的直接原因，2026-02 实测）

现象：数据集 `16307`（Ego 第一视角具身智能，4999 元）的"看了又看"12 条里 **10 条是 1~3 元的鼠标指针皮肤**，另有 1 条是已下架数据。

实测方法与结果（直接调用线上业务接口 `POST https://api.dianshudata.com/datasetRec/recommend`）：

| 目标数据集 | 价格 | 返回的"鼠标指针/数字产品"条数 |
|-----------|------|---------------------------|
| 16307 Ego 具身智能 | 4999 元 | **10 / 12** |
| 8523 小说文档（与之完全无关） | 1 元 | **9 / 12**（且是与 16307 **同一批、基本同一顺序**的商品） |
| 801 英敏特报告 | 2 元 | 0 / 12 |
| 13116 桌宠 | 2.99 元 | 1 / 12 |
| 14058 NCM 格式转换工具 | 2.9 元 | 2 / 12 |

两个**毫不相关**的数据集页面返回同一批热销鼠标指针 → 说明这批结果几乎与"当前页面在看什么"无关，是"平台热销低价商品 + 排序模型缺少目标相关信息"共同造成的。逐条核对状态字段后还发现：

| 字段 | 含义 | 推荐链路是否使用 |
|------|------|-----------------|
| `datasetStatus = 1` | 在售 | — |
| `datasetStatus = 2` | **已下架** | **此前完全未过滤**（实测 16307 的推荐位里就混着 `datasetStatus=2` 的 id=669/8523） |

针对这三条根因，本次分别落到代码：

1. **权重次序被反转 + popular 权重大** → 权重保序（本节的规则）；
2. **排序模型缺少"目标相关"信息**（相关度特征在推理端恒为 0）→ 第二节第 4 条修复 + 第 9 条列表配额；
3. **没有在售状态过滤** → 第二节第 10 条（不可售数据集黑名单与索引剔除）。


另外要区分两种量纲，它们**不能放在一起比大小**：

| 量纲 | 渠道 | 计算方式 |
|------|------|---------|
| 归一化×权重 | behavior / content / vector / popular | 渠道内 Min-Max 归一化到 [0,1]，再乘权重 |
| 绝对加分 | tag / 12cat / category / price / usercf | 归一化后乘一个固定系数，直接加到总分上（`DEFAULT_AUGMENT_WEIGHTS`） |

## 二、本次改动清单（都是小幅度调整）

### 1. 融合层默认权重微调（`app/main.py` → `DEFAULT_CHANNEL_WEIGHTS`）

| 渠道 | 改前 | 改后 | 理由 |
|------|------|------|------|
| behavior | 1.2 | **1.2**（不变） | 个性化仍是点击的第一来源 |
| content | 1.0 | **0.9** | 向线上已验证的 `content_boost` 实验配置（content=0.8 / vector=0.5，CTR 明显更高）小幅靠拢，幅度减半 |
| vector | 0.8 | **0.6** | 同上 |
| popular | 0.02 | **0.05** | 它承担冷启动/长尾兜底，0.02 名义值过低（实际生效值见第 2 条） |
| 12cat | 0.8 | 0.8（不变） | 该键不参与分数融合，只作为排序特征 `channel_weight` 的取值 |

> 提醒：这四项会被 `models/channel_weights.json` 覆盖，因此**这次调整主要影响"没有该文件"或该文件读取失败时的兜底行为**。要让改动真正在线上生效，见第四节。

### 2. 动态权重分配：等额 → 按比例（`app/main.py` → `_compute_dynamic_channel_weights._shift`）

改前：把 `behavior` 权重转移给 `content/vector/popular` 时**按渠道数等额均分**。
后果：`popular` 本来只有 0.02，却因为白捡一份绝对量，实际生效值变成 **0.22（11 倍）**，配置表基本失去意义。

改后：转移量按各目标渠道**当前权重占比**分配（占比为 0 的渠道不参与，权重不会凭空消失）。
以 `/similar`（永远没有用户历史，必然触发这条分支）为例：

| 渠道 | 配置值 | 改前实际生效 | 改后实际生效（约） |
|------|-------|-------------|------------------|
| behavior | 1.2 | 0.60 | 0.60 |
| content | 0.9 | 1.20 | 1.25 |
| vector | 0.6 | 1.00 | 0.83 |
| popular | 0.05 | **0.22** | **0.07** |

现在的"配置值"和"生效值"终于在同一量级上，调参才有意义。

### 3. 辅助渠道系数可配置 + 类别召回小幅加强（`app/main.py`）

原来这五个系数是**写死在函数里的字面量**，无法调、也无法实验：

| 渠道 | 改前（硬编码） | 改后（`DEFAULT_AUGMENT_WEIGHTS`） |
|------|--------------|-------------------------------|
| tag | 0.4 | 0.4 |
| **12cat（行业类别召回）** | 0.5 | **0.6**（小幅加强类别相关性） |
| category（同公司） | 0.3 | 0.3 |
| price（价格分桶） | 0.25 | 0.2 |
| usercf（相似用户） | 0.6 | 0.6 |

同时支持实验覆盖，写法是 `augment_<渠道>_weight`，例如：

```yaml
# config/experiments.yaml
parameters:
  augment_12cat_weight: 0.9   # 加强"同行业类别"召回
```

> 为什么要加 `augment_` 前缀：`models/channel_weights.json` 里**存在** `tag`/`category`/`price`/`usercf`/`12cat` 这些键（由 CTR 统计得到），如果直接复用同名键，某天训练出的 0.03 会把类别召回系数压到几乎为 0。加前缀后两个体系互不干扰。

### 4. 修复排序模型的"训练/推理特征不一致"（重要，影响最大）

排序模型（LightGBM LambdaRank）训练时使用了 5 个与"当前目标数据集"相关的特征：

```
tag_overlap_count, tag_jaccard_similarity, same_top_category,
category_overlap, category_match
```

但推理端这些列**一直是 0**：启动时预计算的静态特征是在 `target_dataset_id=None` 下算的（全部填 0），请求内从未重算。也就是说模型学到的一部分相关性信号在线上完全没参与打分。

本次改动（`app/main.py` 新增 `_compute_relevance_features`，由 `_compute_ranking_features` 在每次请求内按目标数据集重算这 5 列）：

- 5 个特征现在真的有值了，口径与 `pipeline/train_models.py` 完全一致（含 NaN/空标签按"无标签"处理，避免把 `NaN` 解析成字符串 `"nan"` 造成假相似）；
- 顺带把"行业类别词表"统一为 `TOP_CATEGORY_TOKENS`：与 `pipeline/enhance_tags.py` 的 **13 个类别**对齐，并保留历史短名（金融/科技/农业 等）。改前推理端只列了 11 个且与 13 类只有 6 个名字能对上，`same_top_category` 实际上几乎恒为 0；训练端的词表（6 个）也一并统一（`pipeline/train_models.py` 的 `TOP_CATEGORIES_SET`）；
- 加了标签解析缓存（`_split_tags_cached`），避免给每次请求增加可观的解析开销。

> **注意：第 4 条要"完全体现"需要重训排序模型**（Airflow `weekly_model_refresh`）。不重训也不会更差：现在送给模型的特征值与训练时的语义一致，属于修正而不是改动。

### 5. 曝光日志记录"实际生效权重"（`app/main.py` → `_log_exposure`）

`pipeline/evaluate_v2._load_exposure_log` 会读曝光日志 `context` 里的 `channel_weights`，`pipeline/build_training_labels.py` 用它生成训练特征 `channel_weight`——但服务端**从来没写过这个字段**，导致模型看到的 `channel_weight` 是一张固定常量表，与线上真实权重脱钩（一改权重就产生新的训练/推理不一致）。

现在 `/similar` 和 `/recommend/detail` 都会把本次请求实际生效的权重写进曝光日志。副作用：日志每行多了一个小对象（约 100 字节）。

### 6. 把"文档里写了但代码里没有"的三个旋钮做成真的

| 环境变量 | 默认值 | 作用 |
|---------|-------|------|
| `EXPLORATION_EPSILON` | **0.10**（原硬编码 0.15） | 探索率：把结果尾部随机替换成其他数据集的比例。15% 的随机替换对点击率的伤害大于其发现价值，故下调并做成可配 |
| `MMR_LAMBDA` | 0.5（不变） | `/recommend/detail` 的 MMR 相关性/多样性基准 λ |
| `MMR_LAMBDA_SIMILAR` | 0.4（不变） | `/similar` 的 MMR 基准 λ |

实现上用了 `_env_float()`：**环境变量写错（比如写了字母）只会回退默认值并打告警，不会让线上每个请求都抛异常**；取值也会被夹到安全区间（探索率 0~0.5，λ 0.1~0.9）。

### 7. 训练侧兜底表对齐（`pipeline/build_training_labels.py`）

`channel_weight` 特征在"曝光日志缺字段"时使用的兜底权重表，由 `1.5/0.8/0.5` 改为与 `app/main.py` 一致的 `1.2/0.9/0.6`（popular 0.05 不变），减少训练/推理的尺度差异。

### 8. 渠道权重按业务规则重排 + 强制保序（`app/main.py`）

| 渠道 | 改前 | 改后 | 说明 |
|------|------|------|------|
| vector | 0.6 | **1.2** | 与 content 同级，最高 |
| content | 0.9 | **1.2** | 与 vector 同级，最高 |
| behavior | 1.2 | **0.9** | 二级 |
| popular | 0.05 | 0.05 | 三级，且受列表配额约束 |

同时新增 `_enforce_channel_weight_order()`：对 `models/channel_weights.json` 的每日 CTR 覆盖结果做**限幅（±40%）+ 保序（层级间距 15%）**，保证 `vector=content > behavior > popular` 不被训练结果反转，并在日志中打印被修正的渠道（关键字 `Channel weight order enforced`）。

### 9. 最终列表配额：popular ≤3、非目标行业单一类别 ≤3（`app/main.py` → `_apply_list_quotas`）

直接对应领导提出的"12 条推荐里 popular 最多 3 个"：

- MMR 阶段先取 `limit × 3` 的候选池（便于补位）；
- 逐条挑选时统计 **popular 来源数** 与 **各行业类别出现次数**，超配额的候选被跳过；
- **目标数据集自身所属行业豁免类别配额**——鼠标指针详情页返回多个鼠标指针仍然是合理的，只惩罚"与当前页面无关的类别刷屏"；
- 没有类别信息的候选按"未分类"单独计数；
- 极端情况下（候选几乎全是超配额项）会放宽补齐，保证返回条数与 `limit` 一致，并在日志里记录 `List quota applied` / `List quota relaxed`。

### 10. 不可售/已下架数据集过滤（`app/main.py`）

实测确认推荐里会混进 `datasetStatus=2`（已下架）的数据。新增两条通道：

1. **黑名单**：环境变量 `RECO_EXCLUDED_DATASET_IDS="669,8523"` 或 `models/excluded_dataset_ids.json`；
2. **启动时索引剔除**（`_prune_unavailable_datasets`）：把这些 ID 从元数据、标签、行为/内容/向量/热门召回表、标签倒排、12cat 类别索引、价格分桶、相似用户列表里全部移除 → 既不会被召回，也不会进探索池；请求内还有一层兜底（`_drop_excluded_from_scores`）防止命中陈旧索引。

> 根治办法是让特征表带上"在售"标记（业务库 `dataset` 表的 `is_delete` 已在 ETL 处理，但 `datasetStatus` 没有）。当前的排除名单是**可在不改 ETL 的前提下立刻生效**的兜底；建议下一步在 `pipeline/build_features.py` 里把在下售标记透传出来（本文第五节已列为待办）。

### 11. 明确没有改的东西（保证兼容）

- **接口调用方式一律不变**：`/similar/{dataset_id}`、`/recommend/detail/{dataset_id}?user_id=&limit=`、`/hot/trending` 的路径、参数、返回结构（`SimilarResponse` / `RecommendationResponse`）全部保持原样；
- 没有新增/删除接口，没有改字段名，没有改缓存 key（`similar:{id}:{limit}`、`recommend:{id}:{user}:{limit}:{时间桶}`）；
- 没有改动 `config/experiments.yaml` 的现有变体与流量分配（避免直接影响线上流量）；
- 排序模型、召回索引文件格式不变，无需重建索引。

## 三、以后要调"力度/分类"，改哪里

### 场景 A：做 A/B 实验，验证一组权重好坏（推荐，风险最低）

改 `config/experiments.yaml`，**热加载、不用重启**，只影响 `/recommend/detail` 的流量：

```yaml
experiments:
  recommendation_detail:
    variants:
      - name: control
        allocation: 0.4
        parameters: {}
      - name: content_boost
        allocation: 0.3
        parameters: {content_weight: 0.8, vector_weight: 0.5}
      - name: category_boost            # 新增：加强行业类别相关
        allocation: 0.3
        parameters:
          augment_12cat_weight: 0.9
          augment_tag_weight: 0.5
          content_weight: 0.9
```

可用键（任何以 `_weight` 结尾的参数都会被识别为渠道权重）：

| 键 | 对应渠道 | 量纲 |
|----|---------|------|
| `behavior_weight` / `content_weight` / `vector_weight` / `popular_weight` | 融合层四渠道 | 归一化×权重 |
| `augment_tag_weight` / `augment_12cat_weight` / `augment_category_weight` / `augment_price_weight` / `augment_usercf_weight` | 辅助召回加分 | 绝对加分系数 |

每周的 `variant_optimizer` 会按各变体 CTR 自动调整 `allocation`（把流量给表现好的变体），但**它不调参数值**，参数仍需人工设定。

### 场景 B：调"整体兜底力度"（全站生效）

1. 首选：直接改线上 `models/channel_weights.json` 里的数字 → `POST /models/reload`（不用重启）。注意**次日会被流水线按 CTR 重算覆盖**。
2. 想长期生效：改 `app/main.py` 的 `DEFAULT_CHANNEL_WEIGHTS`（需重启容器）**并且**知道它可能被上面的文件覆盖；要彻底摆脱覆盖，得改变 `pipeline/train_channel_weights.py` 的策略（例如改成只产出"相对权重"，或把计算结果限定在默认值的 ±30% 内）。

### 场景 C：调多样性 / 探索 / 质量门槛 / 列表构成

| 目标 | 位置 | 说明 |
|------|------|------|
| 结果更多样 / 更相关 | 环境变量 `MMR_LAMBDA`、`MMR_LAMBDA_SIMILAR` | λ 越大越偏相关性 |
| 增加/减少随机探索 | 环境变量 `EXPLORATION_EPSILON` | 只影响 `/recommend/detail` |
| **限制热门渠道刷屏** | 环境变量 `MAX_POPULAR_SHARE`（默认 0.25） | 12 条里 popular 最多 3 条；设为 1.0 可关闭该限制 |
| **限制某一行业刷屏** | 环境变量 `MAX_OTHER_CATEGORY_SHARE`（默认 0.25） | 非目标行业的单一类别上限；目标自身行业始终豁免 |
| **权重保序强度** | 环境变量 `CHANNEL_WEIGHT_OVERRIDE_BAND`（0.4）、`CHANNEL_WEIGHT_MIN_GAP`（0.15） | 控制 CTR 训练结果能改多少、层间最小差距 |
| **剔除不可售/已下架数据** | 环境变量 `RECO_EXCLUDED_DATASET_IDS` 或 `models/excluded_dataset_ids.json` | 见第二节第 10 条 |
| 砍掉多少尾部候选 | `app/main.py` 的 `FILTER_PERCENTILE`（当前 30，即砍掉最差 30%，候选 <10 个时不启用） | 百分位过滤 |
| 热门召回质量门槛（运行时） | `app/main.py` 中 `price < 1.90 and interaction_count < 66` / `days_inactive > 180 and interaction_count < 30` | 直接改这两个数字 |
| 热门召回质量门槛（训练时） | 环境变量 `POPULAR_MIN_PRICE` / `POPULAR_MIN_INTERACTION` / `POPULAR_MAX_INACTIVE_DAYS` | 每日流水线生效 |
| 返回条数 | 接口参数 `limit`（1~50，默认 10） | 配额会随 limit 等比缩放 |

### 场景 D：调"分类"本身（类别体系）

1. 类别词表：`pipeline/enhance_tags.py` 的 `TOP_CATEGORIES`（当前 13 类）+ 分类阈值 `--threshold`（**默认 0.5**，旧文档写的 0.3 是历史值）；
2. 改完必须重跑 `python -m pipeline.enhance_tags`，重新生成 `models/item_to_categories.json` 与 `models/category_to_items.json`；
3. 同步更新两处词表：`app/main.py` 的 `TOP_CATEGORY_TOKENS`、`pipeline/train_models.py` 的 `TOP_CATEGORIES_SET`（**必须一致**，否则 `same_top_category` 又会退化成恒为 0）；
4. 再重训排序模型（`weekly_model_refresh`）。

## 五、遗留问题（建议后续单独处理，本次未动）

1. **`models/channel_weights.json` 会覆盖代码默认权重**：这是"配置不生效"的最大来源。建议改成"CTR 结果仅在默认值的 ±30% 范围内微调"，或改为按 `behavior/content/vector/popular` 的**相对比例**归一化。调权重前务必先看这份文件。
2. **位置偏差**：后位 CTR 天然低（历史数据：位置 0 约 0.41%，位置 2 约 0.10%），P30 过滤只是掩盖。可在排序目标中加入位置去偏，或引入"成交额/客单价"等商业目标——目前排序标签只有"是否点击"。
3. **`12cat` 仍不在融合层**：类别召回目前是"归一化后的绝对加分"，与 behavior/content 的"归一化×权重"量纲不同，无法直接比较轻重。彻底统一需要把它并入 `_combine_scores_with_weights`（改动较大，建议单独做）。
4. **热门渠道缺"保底槽位"**：popular 现在靠权重竞争（生效值约 0.07），冷启动页面质量仍靠运气。可考虑在 MMR 之后固定保留 1~2 个高质量热门位置。
5. **旧文档中的过时描述**：`docs/RECOMMENDATION_ALGORITHM.md` 曾提到"负分硬截断"（已改为 P30 百分位过滤）、`MMR_LAMBDA`/`EXPLORATION_EPSILON` 环境变量（本次已补齐）、popular 权重 0.1（实际 0.02→0.05）、分类阈值 0.3（实际 0.5），本文与算法文档已同步更新。
