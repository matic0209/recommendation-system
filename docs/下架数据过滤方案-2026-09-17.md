# 下架/已删除数据过滤方案（2026-09-17）

> 本文解决的是："**为什么推荐里会出现已下架、已删除的数据**"——这是推荐质量投诉里最常被提到的一条。
> 结论先行：**推荐链路的候选池里，约 65% 的数据处于"不可推荐"状态**（未发布 / 已删除 / 已下架），
> 而推荐系统此前**完全不知道数据集有状态这回事**。

---

## 一、问题现象

1. 线上"看了又看"里出现页面显示 **"该数据已下架"**、**"该数据已删除"** 的条目。
2. 典型样例：
   - `8658`（孔雀东南飞）：页面"该数据已下架"，**却仍被推荐**（实测出现在 `page_id=16307` 推荐结果第 12 位，渠道 `exploration`）
   - `15769`（白内障智能诊疗数据产品）：页面"该数据已删除"，仍在候选池
3. 由于**探索通道（ε-greedy，占比 15%）是从整个候选池随机抽取**，池子里的坏数据会被随机推到前台，
   表现为"偶尔冒出完全不相关的数据"。

---

## 二、根因

### 2.1 权威判据：`datasetStatus`（平台接口）

实测对照（`POST https://api.dianshudata.com/dataset/datasetDetail`，请求体 `{"datasetId": N}`，**匿名可调用**）：

| 数据集 | 接口 `datasetStatus` | 页面显示 | 数据库三字段 | 结论 |
|---|---|---|---|---|
| 8658 | **2** | 该数据已下架 | publish_status=2, is_delete=0, **is_delisted=1** | 不可推荐 |
| 15769 | 接口返回 `resultCode=2071 数据集不存在` | 该数据已删除 | **publish_status=0**, is_delete=0, is_delisted=0 | 不可推荐 |
| 16307 | **1** | 正常在售 | publish_status=2, is_delete=0, is_delisted=0 | 在售 |

判定规则：**`datasetStatus == 1` 为在售，其余（含"不存在"）均不可推荐。**

### 2.2 业务库字段口径

`dianshu_person_bacnend.dataset` 表相关列：

| 列 | 含义 | 与"不可推荐"的关系 |
|---|---|---|
| `status` | 状态（1待审核 2已通过 3已拒绝） | 审核态；建议 `<> 2` 也排除 |
| `publish_status` | 发布状态（0未发布 1发布中 2发布成功 3发布失败） | `<> 2` → 不可推荐 |
| `is_delete` | 是否删除（0未删除 1已删除） | `= 1` → 不可推荐 |
| `is_delisted` | 是否下架（0未下架 1已下架） | `= 1` → 不可推荐（**8658 属于此类**） |

> 注意：`is_delisted` 这一列在早期版本的建表语句里没有（列是后加的），排查时容易被漏掉。

### 2.3 为什么以前查不到

1. **ETL 从未透传状态字段**：`dataset_features*.parquet`、`dataset_stats.parquet`、`models/*.json`
   里**没有任何状态列**（`datasetStatus`/`is_delete` 零命中）→ 在线服务无从判断。
2. **业务库增量导出（`/dianshu/backup/.../jsons`）只回溯约 2 个月**
   （3,043 个文件 × 30 分钟 ≈ 63 天），更早的状态变更查不到 → 出现"状态盲区"。
3. 增量导出里**没有 `datasetStatus`/`is_delisted` 字段**，无法离线还原平台的判定。

## 三、规模（三个独立来源互相印证）

| 来源 | 口径 | 不可推荐占比 |
|---|---|---|
| 业务库 SQL（`publish_status<>2 OR is_delete=1 OR is_delisted=1`） | 全库 16,359 | **11,057 = 67.6%** |
| 与推荐候选池求交集 | 候选池 15,323 | **10,028 = 65.4%** |
| 平台接口均匀抽样（1,022 个，覆盖 id 20~16364） | 抽样 | **681 = 66.6%** |

业务库明细：

```
数据集总数        16,359
  未发布  publish_status <> 2 :     76
  已删除  is_delete = 1       :  1,044
  已下架  is_delisted = 1     : 10,004
  合计不可推荐                : 11,057
```

**推荐池过滤效果**：`15,323 → 5,295`（**-65.4%**）。

---

## 四、上线前的交叉校验

| 校验 | 方法 | 结果 |
|---|---|---|
| A | 从数据库名单随机抽 60 个 → 平台接口核验 | **60/60 全部非在售**（零误判） |
| B | 从"名单之外"的池内 id 随机抽 60 个 → 接口核验 | 59/60 在售，**1 个漏网（10702）** |
| C | 热销榜（未登录兜底）50 个 → 接口核验 | **50/50 在售** |

**漏网分析**：`10702` 在数据库三字段上都是健康值，但接口稳定返回 `数据集不存在`
→ 数据库规则存在约 **1.7%** 的漏网 → 最终名单应取**数据库名单 ∪ 接口核验结果**。

---

## 五、方案：名单文件 + 启动剔除（已实现）

`app/main.py` 中的三处改动：

| 位置 | 函数 | 作用 |
|---|---|---|
| 启动加载 | `_load_excluded_dataset_ids()` | 读取 `RECO_EXCLUDED_DATASET_IDS` 环境变量与 `models/excluded_dataset_ids.json` |
| 启动剔除 | `_prune_unavailable_datasets()` | 从内存索引中**彻底删除**：元数据、标签、行为/内容/向量召回表、12cat 类别索引、标签倒排、价格分桶、`item_to_tags` |
| 请求过滤 | `_drop_excluded_from_scores()` | 结果层二次过滤（兜底保险） |

**关键点**：剔除是"从 metadata 中删掉"，而**探索池正是取自 `metadata.keys()`**
→ 因此**探索通道也不会再抽到坏数据**（这是 8658 被推出来的直接通道）。

名单文件格式（两种均可）：

```json
[123, 456]
{"ids": [123, 456]}
```

## 六、配套工具

| 工具 | 用途 | 说明 |
|---|---|---|
| `scripts/sync_excluded_from_api.py` | **从平台接口生成名单（推荐）** | 匿名调用，10 并发，无需 DB 权限；网络失败记为 `unknown` 且默认不排除（防误杀）；输出名单 + 明细 CSV |

| `scripts/sample_reco_quality.py` | 线上 vs 新代码的推荐质量采样对比 | 输出 CSV，用于观察期量化 |

## 八、长期自动化

### 方案 A（现在就能用）：每日接口刷新，不需要 DB 权限

```bash
0 3 * * * cd /root/recommendation-system && docker exec airflow-scheduler \
  python /opt/recommend/scripts/sync_excluded_from_api.py \
  --features /opt/recommend/data/processed/dataset_features.parquet \
  --out /opt/recommend/models/excluded_dataset_ids.json \
  --csv /opt/recommend/data/evaluation/dataset_status_report.csv \
  >> /var/log/reco_status_sync.log 2>&1 && docker restart recommendation-api
```

> 实测：接口会随爬取量降速（前 2,000 个约 58 req/s，之后降到 ~18 req/s），
> 15,323 个候选全量核验约需 **20 分钟**，放在凌晨执行即可。

### 方案 B（根治）：ETL 透传状态字段

让业务侧在导出 JSON 中增加 `publish_status / is_delete / is_delisted`（或 `datasetStatus`），
ETL 写入 `dataset_features.parquet`，服务启动时只加载在售数据。
→ 状态变化自动跟随每日流水线，**不再需要维护名单**。

## 九、已知缺口与风险

| # | 事项 | 说明与对策 |
|---|---|---|
| 1 | 数据库规则约 1.7% 漏网（如 10702） | 最终名单取"数据库 ∪ 接口核验"的并集；已据此更新 |
| 2 | 名单更新需重启服务（约 30 秒） | 现状可接受；后续可做 Redis 动态名单实现"秒级生效、不用重启" |
| 3 | "审核中/已拒绝"（`status <> 2`）是否要排除 | 建议排除，数量很小（增量里仅 4 个）；口径确认后加入规则 |
| 4 | 数据集"恢复上架"后需重新生成名单 | 由每夜 cron 自动覆盖 |
| 5 | 名单体量 | 当前 11,057 个 id（89KB），启动时加载为 `set`，开销可忽略 |

## 十、数字（可直接用于汇报）

```
· 全库 16,359 个数据集中，11,057 个（67.6%）处于"未发布/已删除/已下架"状态
· 推荐候选池 15,323 个中，10,028 个（65.4%）不可推荐 → 过滤后仅剩 5,295 个在售
· 未登录兜底热销榜 50 个：100% 在售（问题集中在召回池，不在兜底榜）
· 双向抽样校验：名单内 60/60 命中、名单外 59/60 正确，漏网率约 1.7%（已用并集修复）
```

**一句话结论**：推荐"不相关/推荐已下架数据"的首要原因不是模型，而是
**召回池里三分之二的候选本身就是不应出现的数据**。
