> 编写时间：2026-09-15
> 线上环境：dn051 / `/root/recommendation-system`（compose 项目，API 端口 8090）
> 关联文档：[推荐权重调整说明](./推荐权重调整说明.md)、[推荐系统算法说明](./RECOMMENDATION_ALGORITHM.md)、[环境变量配置](./ENVIRONMENT_CONFIG.md)

## 一、一句话结论

**每日推荐流水线在"模型训练（train_models）"这一步失败，已连续至少 14 天（14/14）；而它是整条链的咽喉——它一失败，后面的"召回索引重建、渠道权重重算、推荐服务重新加载"全部被跳过（14/14 upstream_failed）。**

因此形成三层时间差：

```
数据文件      = 今天（前 6 步任务正常，incremental DAG 也能跑到 train_models）
召回索引/权重 = 2026-03-14（recall_engine / train_channel_weights 从未执行）
推荐服务认知  = 2026-03-14（restart_if_changed 从未执行 → 服务从未重新加载新数据）
```

三层叠加的结果就是业务上看到的现象：**新上架的数据集（如 16307）在服务眼里"不存在"**（没有标签、类别、价格），推荐退化成"全局热销榜 + 最便宜价格档"，于是"具身智能数据集的看了又看里 10 条是 1~3 元鼠标指针"。

**这不是数据坏了，也不是模型坏了——是"数据更新的最后两步"已经失败了半个月。**

## 二、严重性分级

| 级别 | 问题 | 影响范围 |
|------|------|---------|
| **P0** | **每日流水线在 `train_models` 断链（14/14 失败）**，下游 5 个任务全部跳过 | 召回索引、渠道权重、服务刷新全部停摆——**这是所有问题的总根源** |
| **P0** | 元数据/特征快照过期 6 个月（`restart_if_changed` 从未执行） | **所有 2026-03-14 之后上架的数据集**：既推荐不好别人，也不会被别人推荐（在内存索引里不存在） |
| **P0** | 生效的渠道权重与业务规则相反（content 0.083 vs popular 0.323） | 全站，"热销低价商品"挤占推荐位 |
| **P0** | 排序模型依赖的 5 个"目标相关"特征在线上恒为 0（训练时用了，推理时没算） | 全站，排序结果与当前页面几乎无关 |

| **P2** | 特征库 Redis DB1 为空（`dataset_features:*` = 0 条） | 元数据只能靠"启动时读 parquet"，这正是 P0-1 的制度性原因 |

### 3.4.3　另一个 DAG 也在失败（解释了"为什么部分文件是新的"）

`incremental_data_update`（每 4 小时一次：01:26 / 04:00 / 08:00 / 12:00 / 16:00 / 20:00）**同样每次都失败**
（最近 2 天 16 次运行全部 `failed`），但它能跑到 `train_models` 这一步且**部分成功**：

- `data/processed/dataset_features*.parquet` → 今天 16:06（该 DAG 的 `build_features` 产出）
- `models/item_sim_behavior.pkl`、`item_sim_content.pkl`、`item_recall_vector.json`、`rank_model.pkl`、`top_items.json` → 今天 17:04~17:05（该 DAG 的 `train_models` 产出）

**这就是"数据文件是新的、但索引/权重/服务认知是旧的"的原因**：增量 DAG 负责数据与模型文件，主 DAG 负责索引、权重与服务刷新——后者断了。

## 四、问题详情

### P0-1　元数据/特征快照过期（主因）

**现象**：数据集 16307（Ego 第一视角具身智能，4999 元）的"看了又看"12 条里 **10 条是 1~3 元的鼠标指针皮肤**；与之毫不相关的小说数据集 8523 返回**同一批、几乎同一顺序**的鼠标指针。

**实测证据**（直接调用线上业务接口 `POST https://api.dianshudata.com/datasetRec/recommend`）：

| 目标数据集 | 价格 | 鼠标指针类条数 |
|-----------|------|--------------|
| 16307 具身智能 | 4999 元 | **10 / 12** |
| 8523 小说文档 | 1 元 | **9 / 12**（与 16307 同一批） |
| 801 英敏特报告 | 2 元 | 0 / 12 |
| 13116 桌宠 | 2.99 元 | 1 / 12 |
| 14058 NCM 格式转换 | 2.9 元 | 2 / 12 |

**根因（含推断）**：

1. 服务启动于 2026-03-14，`metadata` / `dataset_tags` / `raw_features` / `dataset_stats` / 召回索引**只在启动时加载一次**（`app/main.py` 的 `load_models`）；
2. `POST /models/reload` **只重载模型产物（bundle），不重载元数据/特征**；因此每周的 airflow 重训虽会 reload 模型，但元数据仍是启动时那份；
3. 16307 发布于 2026-08-28，**时序上不可能存在于 3 月 14 日的快照中**（推断，可直接验证：见第六节）；
4. 于是对 16307：`tag` 为空 → tag/12cat 召回为空；`price` 缺失 → 见 P1-2 落进最便宜价格档；排序特征全为 0 → 排序与目标无关；
5. 最终只剩"全局热销榜 + 最便宜价格档"两类候选 → 鼠标指针刷屏。

**影响**：2026-03-14 之后上架的所有数据集都受影响（推荐质量差、且几乎不会出现在别人的推荐里）。

### P0-2　渠道权重被训练结果反转 + popular 实际权重放大 11 倍

- 代码默认表（`app/main.py` 的 `DEFAULT_CHANNEL_WEIGHTS`，旧版）：behavior 1.2 / content 1.0 / vector 0.8 / popular **0.02**；
- `_compute_dynamic_channel_weights` 在"无用户历史"时把 behavior 的权重**按渠道数等额**转移，导致 popular 白捡 0.2 → **实际生效 0.22（配置值的 11 倍）**。而 `/similar`（看了又看）**每次请求都属于"无用户历史"**，所以该放大一直生效；
- `models/channel_weights.json` 每天被 `pipeline/train_channel_weights.py` 按 CTR 重算并覆盖代码默认值，权重次序不受业务约束（可能出现 popular 高于 content 的反常次序）；
- 业务方确认的正确次序为：**vector = content > behavior > popular**。

### P0-3　排序模型的"目标相关"特征在线上恒为 0

- 训练侧使用 5 个与目标数据集相关的特征：`tag_overlap_count`、`tag_jaccard_similarity`、`same_top_category`、`category_overlap`、`category_match`（`pipeline/train_models.py`）；
- 线上推理侧只在**启动时**以 `target=None` 计算过一次（全部为 0）并缓存，请求内不再重算 → `app/main.py` 的 `_prepare_ranker_features` 又把缺失列填 0；
- 结果：模型学到的"目标相关性"信号在线上完全没参与打分，排序结果接近"与目标无关"。

### P0-4　没有"在售/已下架"过滤

- 业务接口字段：`datasetStatus = 1` 在售、`2` 已下架；
- 实测 16307 的推荐位里混有 `datasetStatus=2` 的数据（ids 669、8523）；
- 推荐链路（召回、探索池、兜底列表）**没有任何状态过滤**；ETL 侧只处理了 `is_delete`，未处理 `datasetStatus`。

### P1-1　推荐列表没有配额

无条数/类别约束，单一类别（如"数字产品"）可占满 12 条；popular 渠道可占满 12 条。

### P1-2　目标价格缺失时落进"最便宜价格档"

`_augment_with_multi_channel` 中，目标价格读取失败时按 `0` 处理 → 落入 `bucket "0"`（<100 元）→ 一次性把全部 100 元以下的数据集都加 0.2 分。这是 P0-1 症状的放大器。

### P1-3　`12cat` 类别权重是死配置

`DEFAULT_CHANNEL_WEIGHTS["12cat"]` 不参与分数融合，类别召回只能靠 `_augment_with_multi_channel` 里硬编码的 `0.5`，无法按业务需要调节"分类侧重"。

### P2　其他

- 文档与代码不一致：算法文档仍写"负分硬截断"（实际已是百分位过滤）、写有不存在的环境变量 `MMR_LAMBDA`/`EXPLORATION_EPSILON`（现已在代码中补齐）、popular 权重 0.1（实际 0.02）、分类阈值 0.3（实际 0.5）。
- `scripts/deploy_prod.sh` 检查 `models/ranking_model.txt`，但代码加载的是 `rank_model.pkl` → 部署时会出现无意义的"排序模型文件不存在"告警。
- airflow-scheduler 日志中的 Postgres collation 警告（2.41 vs 2.36）属环境警告，当前无功能影响。
- 训练侧优先使用 `dataset_features_v3.parquet`（152992 行），服务侧元数据约 15322 条 → 口径是否一致待确认。

## 五、修复方案

### 第一批：已完成（在本地仓库，尚未发版）——"让规则正确"

| 改动 | 内容 | 文件 |
|------|------|------|
| 权重次序保序 | 强制 `vector = content > behavior > popular`；对每日 CTR 结果的覆盖做限幅（±40%）与层间距约束（≥15%），训练结果不能再反转次序 | `app/main.py` |
| 列表配额 | 12 条里 popular 来源 ≤3；非目标行业的单一类别 ≤3；目标自身行业豁免；条数不足时放宽补齐 | `app/main.py` |
| 相关度特征修复 | 5 个"目标相关"特征改为**每次请求按当前目标重算**（修复 P0-3）；类别词表与 `enhance_tags` 的 13 类对齐 | `app/main.py`、`pipeline/train_models.py` |
| 动态权重按比例转移 | 修掉"popular 被白捡 0.2"（修复 P0-2），生效值从 0.22 回到约 0.07 | `app/main.py` |
| 在售过滤（黑名单兜底） | `RECO_EXCLUDED_DATASET_IDS` 或 `models/excluded_dataset_ids.json`；启动时从元数据、标签、行为/内容/向量/热门召回表、标签倒排、类别索引、价格分桶、相似用户列表**全部剔除**，请求内再兜底一次 | `app/main.py` |
| 参数化 | `EXPLORATION_EPSILON`（默认 0.15→0.10）、`MMR_LAMBDA`、`MMR_LAMBDA_SIMILAR`、`MAX_POPULAR_SHARE`、`MAX_OTHER_CATEGORY_SHARE`、`CHANNEL_WEIGHT_OVERRIDE_BAND`、`CHANNEL_WEIGHT_MIN_GAP` | `app/main.py` |
| 曝光日志 | 记录本次请求**实际生效的渠道权重**，为后续训优提供数据 | `app/main.py` |
| 自检脚本 | `scripts/verify_channel_weight_changes.py`（60 项断言，已全部通过） | 新增 |

**改动规模**：`app/main.py` 约 +400 行（其中约一半是注释/文档字符串），`pipeline/build_training_labels.py` ≈10 行，`pipeline/train_models.py` ≈12 行；**接口、参数、返回结构、缓存键零变化**。

### 第二批：建议尽快做（解决"必须重启才能刷新"的制度性问题）

1. **扩展 `POST /models/reload`，让它同时重建元数据/标签/类别索引**（现在只重载模型产物）→ 以后数据更新不再依赖重启；
2. **目标价格缺失时跳过"价格分桶召回"**，并打告警日志（修复 P1-2 的放大器）；
3. 可选：加一个"快照年龄"健康检查（`/health` 里返回元数据加载时间），超过 N 天告警。

**改动规模**：约 50~80 行，集中在 `app/main.py` 的 `reload_models` 与 `_augment_with_multi_channel`。

### 第三批：根治（需要数据/业务侧配合）

1. **ETL 带上在售标记**：确认业务 JSON 导出里是否有 `status`/`datasetStatus`/`is_delete` 字段（第三节命令可查），有则直接在 `pipeline/build_features.py` 过滤；没有则需要业务侧加字段；
2. **热门榜口径调整**：`pipeline/train_models.py` 的 `build_popular_items` 提高价格门槛/排除"低价高销"商品，避免热销榜被 1~3 元商品占满；
3. **重训排序模型**：让修复后的相关度特征真正进入模型（等待一周一次的 `weekly_model_refresh`）；
4. **确认 v3 特征口径**与训练/服务一致性。

## 六、验证与上线

### 6.1 先验证（不动生产）

用影子容器验证"新快照 + 新代码"的效果（详细步骤见 [推荐权重调整说明](./推荐权重调整说明.md) 与本文附注）：

```bash
# 影子实例：复用生产镜像 + 挂新代码 + models 只读 + 缓存换到 Redis DB9（隔离）
docker run -d --name reco-shadow --network <生产网络> -p 18090:8000 \
  -v /root/reco-shadow/repo/app:/app/app:ro \
  -v /root/reco-shadow/repo/pipeline:/app/pipeline:ro \
  -v /root/reco-shadow/repo/config:/app/config:ro \
  -v /root/recommendation-system/models:/app/models:ro \
  -v /root/reco-shadow/data:/app/data \
  --env-file /root/reco-shadow/env.list \
  recommend-recommendation-api
```
> 关键：`env.list` 里 `REDIS_URL` 必须改成 `redis://redis:6379/9`（否则影子写入的缓存会被生产读走），`SENTRY_DSN` 置空。
> 影子容器**启动时会加载今天的 parquet 快照**，因此它同时验证了"快照刷新"与"代码修复"两件事。

### 6.2 上线（一次发版解决全部）

任何代码改动都需要重建容器，**"重启"就是这次发版本身**，不是额外操作。三种做法：

| 方式 | 中断时间 | 说明 |
|------|---------|------|
| 低峰期发版（推荐） | 30~90 秒 | 凌晨低峰执行 `docker compose build recommendation-api && docker compose up -d recommendation-api` |
| nginx 切上游（近零中断） | 秒级 | 先用 18090 起新版本 → 验证 → 改 nginx upstream 指向 18090 → 停旧容器 |
| 只重启不换代码 | 30~90 秒 | 仅验证"快照过期"是否为根因（零代码改动），适合先做小实验 |

**发版前必做**：
```bash
docker tag recommend-recommendation-api recommend-recommendation-api:backup-$(date +%Y%m%d)   # 镜像快照（否则无法回滚）
cp models/channel_weights.json models/channel_weights.json.bak
```

**回滚**：`git checkout <旧提交> && docker compose build recommendation-api && docker compose up -d recommendation-api`，或直接用备份镜像标签重新起容器。**无数据结构变更、无接口变更，回滚风险低。**

### 6.3 验收标准

| 验收项 | 标准 | 检查方式 |
|--------|------|---------|
| 目标相关 | 16307 页面的推荐与"具身智能/农业/多模态"相关，鼠标指针类 ≤3 条 | `curl localhost:8090/similar/16307?limit=12` 看标题与 `reason` |
| 热门占比 | 12 条里 `reason` 含 `popular` 的 ≤3 条 | 同上 |
| 在售 | 黑名单/已下架 id 不出现 | 对比 `datasetStatus` |
| 一致性 | 两个不相关页面不再返回同一批结果 | 16307 vs 8523 |
| 性能 | 响应时间与改动前同量级（`Recommendation compute completed` 日志） | 日志对比 |
| 监控 | 出现 `Channel weight order enforced`、`List quota applied`、`Pruned unavailable datasets` | `docker logs` |

### 6.4 待确认清单（需要业务/运维提供）

2. 可接受的生产中断窗口（决定采用哪种上线方式）；
3. `dataset_features_v3.parquet`（152992 行）的生成口径，与服务侧 15322 条是否一致。
