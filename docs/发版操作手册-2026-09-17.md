
`--check` 只做前置检查、不改任何东西（窗口前跑一次最保险）。

## 1.5 发版审计记录（2026-09-17，语义级对照）

**方法**：不使用行级 diff（那会漏掉语义变化），改用四种权威对照：
① `docker compose config` 解析后的**完整配置**对比；② 接口路由集合对比；
③ import 依赖差异；④ 逐一核对代码里真实的文件加载点 → 用**单元测试/功能测试**验证。

| 检查项 | 方法 | 结果 |
|---|---|---|
| 容器配置语义 | 两边 compose 用同一 env 解析后 diff | ✅ 仅 9 处 `restart: unless-stopped` 差异，**挂载/环境变量/端口零差异** |
| 接口契约（调用方式不变） | 旧版 vs 新版 提取路由集合 | ✅ 完全一致（7 个接口，无新增/删除） |
| 新增依赖 | import 差异 | ✅ 仅新增标准库 `functools.lru_cache` |
| 下架过滤逻辑 | `scripts/test_excluded_filter.py`（28 项断言） | ✅ 全覆盖：名单解析/全索引剔除/脏数据容错/请求期兜底 |
| 重启触发逻辑 | 函数级功能测试（伪造 models 目录） | ✅ 10 个产物任一变化/删除都能触发 |
| 影子端到端 | `scripts/deploy_check.sh reco-shadow` | ✅ 需在发版前跑，见第 4 节 |

**审计中发现并已修复的问题（都在本次发版里）**

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 我合并 compose 时把 `/var/run/docker.sock` 挂到了 `airflow-init`（一次性容器），服务器原本挂在 `airflow-scheduler` | `restart_if_changed` 无法重启 API → **"索引更新了但服务还用旧数据"静默失效** | 归位到 scheduler（已由解析后配置对比独立验证） |
| 2 | `_prune_unavailable_datasets` 在循环内重建字符串集合（`{str(i) for i in excluded}`） | 启动时约 5500 万次字符串转换 → 启动多花几十秒 | 循环外预计算 `excluded_str` |
| 3 | 同函数里 `int(entry[0])` / `int(entry.get(...))` 无异常保护 | 索引里出现脏数据 → **启动直接崩溃** | 加 `try/except`，脏数据保守保留 |
| 4 | `restart_service.sh` 只监控 3 个文件，而服务启动时加载 **10 个**产物 | `channel_weights.json`/`item_sim_*.pkl`/`top_items.json` 等更新后服务仍用旧值 | 扩展为完整清单（含 4 项新增，已验证触发） |

**尚未验证（诚实清单）**

| 项 | 说明 |
|---|---|
| 构建出的**镜像本身** | 影子实例用的是"生产镜像 + 挂载新代码"，**没有验证新构建的镜像** → 因此发版流程新增"金丝雀"环节（第 4.5 节）用新镜像起实例验收 |
| 全站页面 | 验收抽样 12 个页面，非全量；断言是"无下架数据泄漏 + 热门 ≤3" |
| 训练链路重训效果 | 5 个相关度特征修复要等 `weekly_model_refresh` 重训后才完全体现 |

> 为什么 `app/main.py` 必须重建镜像：生产 `recommendation-api` 只挂载
> `./data ./models ./logs ./cache`，**没有挂载 `app/`** → 改代码必须打进镜像。
> 反过来 `pipeline/`、`airflow/`、`scripts/` 是挂载进 airflow 容器的 → 只需重启 airflow。

## 2. 服务器：备份 + 拉取（可回滚的基础）

### 2.0 配置与环境变量不会被动到（已核实）

本次发版涉及的 27 个文件里**没有** `.env*`、也没有 `config/`，只有代码/文档/脚本：

| 文件 | 是否被 git 跟踪 | 拉取会不会动 |
|---|---|---|
| `.env` | **未跟踪** | ❌ 不会（Git 不碰未跟踪文件） |
| `.env.prod` | **未跟踪** | ❌ 不会 |
| `.env.memory` | 被跟踪 | ❌ 本次提交未修改它 → 合并不动；服务器上的本地改动也保留 |
| `config/experiments.yaml` | 被跟踪 | ❌ 同上（A/B 流量配置保持不变） |
| `models/`、`data/`、`logs/`、`cache/` | 未跟踪/忽略 | ❌ 不会 |

## 4.5 金丝雀：用【新构建的镜像】再验一遍（补齐影子的盲区）

影子实例是"**生产旧镜像** + 挂载新代码"，它验证不到**构建产物本身**（Dockerfile 打包进去的 app/config/pipeline）。所以发版前再用**新镜像**起一个隔离实例验收：

```bash
cd /root/recommendation-system

# 1) 确认备份标签在位（第 2 步打的）
docker images --format '{{.Repository}}:{{.Tag}}' | grep recommend-recommendation-api

# 2) 构建新镜像
#    ⚠️ .dockerignore 没有排除 data/ 与 models/，构建上下文约 2GB，
#       build 可能耗时数分钟（磁盘也要留够空间）—— 不是卡住，属正常。
docker compose build recommendation-api
docker tag recommend-recommendation-api recommend-recommendation-api:candidate-$(date +%Y%m%d-%H%M)

# 3) 用新镜像起金丝雀（独立端口 / Redis DB9 / 独立曝光日志，不接生产流量）
docker rm -f reco-canary >/dev/null 2>&1
CANARY_TAG=$(docker images --format '{{.Repository}}:{{.Tag}}' | grep 'recommend-recommendation-api:candidate' | sort | tail -1)
docker run -d --name reco-canary \
  --network "$(docker inspect recommendation-api --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}{{end}}')" \
  -p 127.0.0.1:18091:8000 --user root \
  -v /root/recommendation-system/models:/app/models:ro \
  -v /root/recommendation-system/data/processed:/app/data/processed:ro \
  -v /root/reco-shadow/data/evaluation:/app/data/evaluation \
  --env-file /root/reco-shadow/env.list \
  "$CANARY_TAG" uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 2

sleep 90
bash scripts/deploy_check.sh reco-canary      # 必须退出码 0
```

**金丝雀通过 → 才允许推进到第 5 节。**
> `docker compose build` 会覆盖 `recommend-recommendation-api` 标签，但**正在运行的容器仍用原镜像 ID**，不受影响；回滚用的 `:backup-*` 标签已打好。
> 收尾：`docker rm -f reco-canary`（不影响生产）。

## 7. 回滚（出问题按档位执行）

### R1：服务异常 / 验收不通过 → 回滚镜像（60~90 秒）

**判断**：`/health` 不健康、接口 5xx、验收脚本报错、页面明显异常。

```bash
cd /root/recommendation-system
docker images --format '{{.Repository}}:{{.Tag}}' | grep 'recommend-recommendation-api:backup' | sort | tail -3
# ↑ 复制最近的那个 backup tag（例如 recommend-recommendation-api:backup-20260917-2230）

docker tag recommend-recommendation-api:backup-20260917-2230 recommend-recommendation-api
docker compose up -d --force-recreate recommendation-api
for i in $(seq 1 40); do curl -sf -m 5 localhost:8090/health >/dev/null 2>&1 && break; sleep 5; done
curl -s localhost:8090/health; echo
```

**回滚后的验证标准**（注意：旧版 `/similar` 本来就是坏的，所以**不要**用 `deploy_check.sh` 判断）：
```bash
curl -s "localhost:8090/similar/16307?limit=12" | head -c 200      # 有返回即可
docker exec recommendation-api sh -c "tail -5 /app/logs/*.log"      # 无大量异常堆栈
```

### R2：名单导致结果异常（结果变少/不相关）→ 摘掉名单（30 秒）

**判断**：`/similar` 返回条数明显变少、或推荐质量反而下降。

```bash
cd /root/recommendation-system
mv models/excluded_dataset_ids.json /root/release_backup_$(date +%Y%m%d-%H%M)/excluded_dataset_ids.json.off
docker restart recommendation-api      # 30 秒
curl -s "localhost:8090/similar/16307?limit=12" | head -c 200
```
> 摘掉名单后，已下架数据会重新出现——这是"用旧的坏行为换取可用性"，属可控回退。

### R3：流水线异常（任务失败/日志报模板错）→ 回退代码（≤10 秒）

```bash
cd /root/recommendation-system
git log --oneline -5
git revert --no-edit <可疑提交>        # 或 git reset --hard $(cat /root/release_backup_*/pre_deploy_head.txt)
docker restart airflow-scheduler
```

### R4：全部回退（最坏情况）

```bash
cd /root/recommendation-system
git reset --hard "$(cat /root/release_backup_*/pre_deploy_head.txt)"   # 代码回到发版前
mv models/excluded_dataset_ids.json /tmp/ 2>/dev/null                   # 名单摘除
docker tag recommend-recommendation-api:backup-<发版前时间戳> recommend-recommendation-api
docker compose up -d --force-recreate recommendation-api
docker restart airflow-scheduler
```
**回退后核对**：`md5sum app/main.py` 应等于 `pre_deploy_md5.txt` 里的值。
