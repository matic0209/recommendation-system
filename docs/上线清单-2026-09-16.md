## 二、影子验证（不影响生产，发版前必做）

用生产镜像 + 待发版代码，在独立端口/独立 Redis DB 上跑真实数据：

```bash
# 1) 准备（只读挂载生产模型与数据，代码用待发版版本）
mkdir -p /root/reco-shadow/data && cd /root/reco-shadow
#    把待发版代码放到 /root/reco-shadow/repo（git clone 或 rsync 当前工作目录）

# 2) 生成隔离环境变量（Redis 换 DB9、Sentry 置空）
docker inspect recommendation-api --format '{{range .Config.Env}}{{println .}}{{end}}' \
  | grep -vE '^(PATH|HOSTNAME|HOME|LANG|LC_|PYTHON|GPG|TERM|DEBIAN)' > env.list
sed -i 's#\(REDIS_URL=redis://[^/]*\)/0#\1/9#' env.list
sed -i 's#^SENTRY_DSN=.*#SENTRY_DSN=#' env.list
NET=$(docker inspect recommendation-api --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}{{end}}')

# 3) 起影子实例（18090）
docker run -d --name reco-shadow --network "$NET" -p 18090:8000 \
  -v /root/reco-shadow/repo/app:/app/app:ro -v /root/reco-shadow/repo/pipeline:/app/pipeline:ro \
  -v /root/reco-shadow/repo/config:/app/config:ro \
  -v /root/recommendation-system/models:/app/models:ro \
  -v /root/reco-shadow/data:/app/data --env-file /root/reco-shadow/env.list \
  recommend-recommendation-api

# 4) 对比（先清影子缓存：只清 DB9，绝不动 DB0）
docker exec redis redis-cli -n 9 flushdb
for p in 8090 18090; do
  echo "== 端口 $p =="
  curl -s "localhost:$p/similar/16307?limit=12" | python3 -c "
import sys,json,collections
d=json.load(sys.stdin); it=d.get('similar_items',[])
c=collections.Counter(x['reason'] for x in it)
pop=sum(v for k,v in c.items() if 'popular' in k or 'fallback' in k)
print(' 条数',len(it),'| popular',pop,'| 渠道',dict(c))
print(' ids',[x['dataset_id'] for x in it])"
done
```

**验收标准**：影子实例（18090）返回 12 条里 popular ≤ 3；`content/vector/tag` 渠道 ≥ 6 条；结果明显比 8090 更相关。
验证完删除影子实例：`docker rm -f reco-shadow`（**不要动 DB0**）。

## 三、上线

### A. 流水线代码（挂载进容器，无需重建，零中断）

```bash
cd /root/recommendation-system
git fetch origin && git merge --ff-only origin/feature/recommendation-category-enhancement
docker restart airflow-scheduler          # 让 DAG/脚本改动生效
docker ps --format '{{.Names}} {{.Status}}' | grep airflow-scheduler
```

### B0. 下架/已删除名单（数据文件，必须与 B 同时上线）

```bash
scp models/excluded_dataset_ids.json yc-108:/root/recommendation-system/models/
```

* 名单由 `app/main.py` 在**启动时**读取，并从内存索引中彻底剔除（含探索池）——所以必须与 B 一起上线（或上线后立即重启一次服务）。
* 名单**不入库**：它是运行期数据，入库后每次刷新都会弄脏工作区，挡住 `git merge --ff-only`。
* 验收：`docker logs recommendation-api 2>/dev/null | grep -i Excluded`
  → 应输出 `Excluded 11057 datasets from in-memory indices`（数量以名单文件为准）。
* 方案与数字详见 `docs/下架数据过滤方案-2026-09-17.md`。

### B. 推荐服务（需重建镜像，中断 30~90 秒）

```bash
cd /root/recommendation-system
docker tag recommend-recommendation-api recommend-recommendation-api:backup-$(date +%Y%m%d)   # ★回滚用
docker compose build recommendation-api
docker compose up -d recommendation-api
# 等 60~90 秒（加载 240MB 模型产物）
docker logs --tail 20 recommendation-api | grep -E "Model artifacts loaded|startup complete"
curl -s localhost:8090/health
```

### C. 让 compose 的自愈策略生效（可选，低峰期）

```bash
# ✅ 推荐：用 docker update 零中断补策略（不重建容器）
docker update --restart unless-stopped redis postgres-airflow report-viewer notification-gateway

# ✅ 可选：对这几个服务重建，使容器配置与 compose 文件一致（无副作用）
docker compose up -d mlflow prometheus alertmanager grafana

# ❌ 不要执行不带服务名的 `docker compose up -d`：
#    它会重建 redis / postgres-airflow / airflow-webserver / airflow-scheduler，
#    可能打断正在运行的流水线任务。
```

## 六、上线后须知（写进发布说明，避免误会）

1. **缓存 300 秒**：`/similar` 结果缓存在 Redis DB0。发版后最初几分钟可能仍返回旧结果——不是没生效。需要立刻看到效果就清一次：`docker exec redis redis-cli -n 0 flushdb`（**只清 DB0**）。
2. **服务每天可能被自动重启一次**：`restart_if_changed` 修好后会真正生效；只要 `item_to_tags_enhanced.json` / `category_index.json` / `rank_model.pkl` 内容变化就会重启服务（约 30-90 秒）。这是**预期行为**（让服务重新加载最新数据快照），不是故障。
3. **热门来源会被压到 ≤3 条**：这是业务规则的显式要求；若某页面本身属于热销品类（如鼠标指针页），其"同行业"条目不受该配额限制。
4. **监控已恢复**：prometheus/alertmanager/grafana 已随本次修复拉起，关键任务失败应能收到告警（建议再核对一次告警通道是否真的能送达）。
5. **仍需人工关注的遗留项**：
   - 12 类行业分类与标签增强**未覆盖全部数据集**（新上架数据集当天仍不会被识别，要等当日流水线）；
   - ETL 未透传"在售状态"字段，目前靠黑名单 `RECO_EXCLUDED_DATASET_IDS` / `models/excluded_dataset_ids.json` 兜底；
   - `dataset_features_v3.parquet`（15 万行）与在线服务口径（1.5 万条）仍不一致，待确认是否应统一。

本地用**同一份数据 + 新代码**（Docker，arm64）实测：

| 跨页面重复率 | 17%~33% | ✅（生产原为同一批≈100%） |

**过程中发现并修复的 2 个严重问题**（仅靠静态检查发现不了，必须真实起服务打请求）：
1. `/similar` 因重复代码块引用未定义变量 `user_id`，**每次请求都抛异常并降级为 `fallback:popular`**——若直接上线会比现状更差；
2. 配额放宽时按原排名放行，会把刚挡下的热销品又填回来（实测 12 条出现 4 条 popular，超上限）。
